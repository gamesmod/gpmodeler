# 7. Паттерны аналитических хранилищ

Greenplum и Cloudberry чаще всего используют как корпоративное хранилище данных (DWH) или
платформу для аналитики. Ниже — устоявшиеся паттерны и то, как их физически раскладывать в MPP.

## Слои хранилища

| Слой | Схема | Что лежит | Физика |
|---|---|---|---|
| Staging | `stg` | сырые данные источника «как есть», одна загрузка | heap или `ao_row` без сжатия, `RANDOMLY`, очищается после загрузки |
| ODS / сырой слой | `ods` | история данных источника в структуре источника | `ao_row`/`ao_column`, секции по дате загрузки |
| Детальный слой | `dds` | интегрированная модель: 3НФ, Data Vault или anchor | распределение по осям предметной области, секции по бизнес-дате |
| Витрины | `dm` | звёзды и плоские таблицы под отчёты | `ao_column` + `zstd`, распределение под основные соединения |

Схемы для слоёв упрощают права доступа: аналитики читают `dm`, процессы загрузки пишут в `stg`
и `dds`.

## Звезда и снежинка

**Схема «звезда»** — таблица фактов в центре и денормализованные измерения вокруг.

* **Факты** — события или состояния с числовыми мерами (сумма, количество) и ссылками на измерения.
  Определите **зерно** факта до того, как добавлять колонки: «одна строка — одна позиция чека»,
  «один счёт за один день».
* **Измерения** — описательные атрибуты (клиент, товар, дата, филиал) с суррогатным ключом.

Физическая раскладка в MPP:

* таблица фактов — `ao_column` + `zstd`, секции по дате, распределение по ключу самого большого
  измерения, с которым она соединяется (например, `customer_key`);
* крупное измерение (клиенты, счета) — распределение по тому же ключу, что у фактов, тогда
  соединение локальное;
* мелкие измерения (дата, валюта, филиал, канал) — `DISTRIBUTED REPLICATED`;
* измерения средних размеров (товары, сотни тысяч или миллионы строк) — распределение по своему
  ключу; оптимизатор обычно рассылает их `Broadcast Motion`, и это дёшево.

**Снежинка** нормализует измерения (товар → категория → группа). В MPP каждое дополнительное
соединение может стоить перемещения данных, поэтому для витрин звезда предпочтительнее. Снежинку
оправдывают очень большие измерения с повторяющимися иерархиями.

### Календарь

Измерение даты стоит создать всегда: рабочие и праздничные дни, недели, кварталы, финансовый год.
Это маленькая реплицированная таблица, которая избавляет запросы от вычислений над датами.

## Медленно меняющиеся измерения (SCD)

| Тип | Как хранится история | Когда |
|---|---|---|
| SCD0 | не меняется | неизменяемые атрибуты (дата рождения) |
| SCD1 | перезапись | исправления ошибок, атрибуты без ценности истории |
| SCD2 | новая строка на каждое изменение, `valid_from`/`valid_to`, флаг текущей версии | основной способ хранить историю |
| SCD3 | колонка «предыдущее значение» | нужна только одна предыдущая версия |

Особенности SCD2 в MPP:

* закрытие версии — это `UPDATE`, а в AO-таблицах он дорогой. Для больших измерений делайте
  загрузку через пересборку: вычислить новое состояние в отдельной таблице и заменить
  (`EXCHANGE PARTITION`, переименование или `TRUNCATE` + `INSERT`);
* распределяйте по **естественному** ключу сущности или по суррогатному ключу сущности, общему для
  всех версий, а не по ключу версии. Тогда все версии одного клиента лежат на одном сегменте и
  соединяются с фактами локально;
* используйте полуинтервал `[valid_from, valid_to)` и «бесконечную» дату для текущей версии
  (`9999-12-31`) вместо `NULL`, чтобы условия по дате работали с отсечением и были простыми.

## Data Vault

Data Vault 2.0 хорошо подходит для детального слоя, который интегрирует много источников:

* **Hub** — уникальные бизнес-ключи сущности и хеш-ключ от них;
* **Link** — связи между хабами, хеш-ключ от комбинации ключей;
* **Satellite** — атрибуты хаба или линка с историей изменений.

В MPP:

* хеш-ключи вычисляются детерминированно на каждом сегменте, без последовательностей, — это
  хорошо масштабирует параллельную загрузку;
* распределяйте хаб и все его сателлиты по хеш-ключу хаба: соединение хаба с сателлитами локальное;
* линк распределяйте по хеш-ключу самого большого из связанных хабов;
* модель порождает много соединений, поэтому для отчётов поверх неё строятся витрины (звёзды),
  а не запросы напрямую к хабам и сателлитам;
* сателлиты обычно `ao_column` с секциями по дате загрузки, хабы и линки — `ao_row` или heap.

## Широкие плоские витрины

Для BI-инструментов и машинного обучения иногда выгоднее одна широкая денормализованная таблица
(сотни колонок), чем звезда. В колоночном хранении это работает хорошо: запрос читает только
нужные колонки, а соединения не нужны. Цена — пересборка при изменении измерений и дублирование
данных.

## Загрузка данных

* **Пакетно, а не построчно.** Каждый отдельный `INSERT` — распределённая транзакция с рассылкой
  на сегменты и двухфазной фиксацией, поэтому построчная загрузка очень медленная. Используйте
  `COPY`, внешние таблицы или `INSERT ... SELECT` из staging.
* **Внешние таблицы через `gpfdist`.** Файлы раздаёт процесс `gpfdist`, и каждый сегмент читает
  свою часть параллельно, минуя координатор. Утилита `gpload` оборачивает этот механизм.
* **PXF** (Platform Extension Framework) — внешние таблицы над HDFS, Hive, S3, другими СУБД по JDBC.
  Подходит для чтения больших внешних наборов и для архива, вынесенного из базы.
* **Сценарий загрузки:** внешняя таблица → `stg` (`RANDOMLY`) → проверки качества → `INSERT ... SELECT`
  или `EXCHANGE PARTITION` в целевую таблицу с нужным распределением → `ANALYZE`.
* **Сортировка при вставке.** Если в колоночной таблице колонки сжаты `rle_type` или запросы
  фильтруют по колонке, коррелирующей с порядком, вставляйте данные отсортированными
  (`INSERT ... SELECT ... ORDER BY`): это улучшает сжатие и работу BRIN-индексов.
