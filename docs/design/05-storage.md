# 5. Хранение и сжатие

В Greenplum и Cloudberry у каждой таблицы есть способ хранения (access method). От него зависят
скорость сканирования, стоимость изменений, объём на диске и доступные виды сжатия.

## Способы хранения

| Хранение | GP6 | GP7, CBDB | Подходит для | Плохо для |
|---|---|---|---|---|
| heap | по умолчанию | `USING heap` | маленьких таблиц, частых `UPDATE`/`DELETE`, справочников, staging | больших таблиц фактов: нет сжатия, медленное сканирование |
| append-optimized, строки | `WITH (appendoptimized=true, orientation=row)` | `USING ao_row` | больших таблиц, из которых читают большинство колонок | частых точечных изменений |
| append-optimized, колонки | `WITH (appendoptimized=true, orientation=column)` | `USING ao_column` | широких таблиц фактов, где запросы читают малую долю колонок | частых `SELECT *`, мелких таблиц, точечных изменений |
| PAX | — | `USING pax` (Cloudberry 2.x) | гибридного доступа: колоночная организация внутри блоков, статистика для пропуска блоков | проверяйте зрелость в своей версии перед боевым применением |

В GP6 параметр `appendoptimized` также пишется как `appendonly`, это синонимы.

### Heap

Обычные страницы PostgreSQL с MVCC. Изменения дешёвые, но удалённые и старые версии строк
остаются до `VACUUM`, а сжатия нет. Используйте heap для таблиц до нескольких гигабайт и для всего,
что часто обновляется.

### Append-optimized (AO)

Оптимизированы для массовой вставки и сканирования. Удаление и обновление поддерживаются, но
работают через карту видимости (visimap): старые строки физически остаются в файле, пока `VACUUM`
не перепишет сегментный файл. Такие операции берут блокировку, которая не даёт параллельно
изменять ту же таблицу, поэтому AO не подходят для конкурентных изменений.

**Строковые AO (`ao_row`)** хороши, когда запросы читают строку почти целиком: широкие выгрузки,
таблицы с небольшим числом колонок.

**Колоночные AO (`ao_column`)** хранят каждую колонку в отдельном файле. Запрос, который читает
5 колонок из 200, читает с диска примерно 5/200 объёма. Однотипные значения в колонке сжимаются
намного лучше. Цена — число файлов: колонки × секции × сегменты. Поэтому колоночное хранение
неудачно для небольших таблиц и для таблиц с тысячами секций.

## Сжатие

Сжатие доступно только для AO-таблиц (и PAX). Оно уменьшает дисковый ввод-вывод ценой процессора;
на аналитической нагрузке это почти всегда выгодно, потому что узкое место — диск.

| Алгоритм | Уровни | Где | Комментарий |
|---|---|---|---|
| `zstd` | 1–19 | GP6, GP7, CBDB | выбор по умолчанию: хорошее сжатие и быстрая распаковка |
| `zlib` | 1–9 | GP6, GP7, CBDB | совместимость со старыми моделями, медленнее `zstd` при том же коэффициенте |
| `quicklz` | 1 | только GP6 | удалён в GP7; при миграции замените на `zstd` |
| `rle_type` | 1–4 | только колоночные | кодирование повторов; отлично для отсортированных колонок и колонок с малым числом значений |
| `none` | — | все | без сжатия |

Практические уровни:

* `zstd` 1–3 — горячие данные, частые загрузки, когда важна скорость записи;
* `zstd` 4–7 — основной режим для таблиц фактов;
* `zstd` 9 и выше — архив; запись заметно медленнее, выигрыш в размере обычно небольшой.

Подбирайте уровень на реальной выборке: загрузите несколько миллионов строк с разными
настройками и сравните `pg_total_relation_size` и время типовых запросов.

### Сжатие по колонкам

У колоночной таблицы сжатие задаётся для каждой колонки отдельно:

```sql
CREATE TABLE events (
    event_time   timestamptz ENCODING (compresstype = zstd, compresslevel = 5),
    status       smallint    ENCODING (compresstype = rle_type, compresslevel = 2),
    payload      text        ENCODING (compresstype = zstd, compresslevel = 9),
    DEFAULT COLUMN ENCODING (compresstype = zstd, compresslevel = 3)
)
USING ao_column              -- в GP6: WITH (appendoptimized = true, orientation = column)
DISTRIBUTED BY (device_id);
```

`rle_type` эффективен, если одинаковые значения идут подряд, то есть данные загружаются
отсортированными по этой колонке.

## Размер блока

Параметр `blocksize` (от 8 КБ до 2 МБ, по умолчанию 32 КБ) задаёт размер блока AO-таблиц. Значение
по умолчанию подходит в большинстве случаев; увеличение иногда помогает очень широким
последовательным сканированиям и почти всегда увеличивает потребление памяти. Меняйте его только
по результатам замеров.

## Как выбрать

1. Таблица маленькая (до единиц гигабайт) или часто изменяется — **heap**.
2. Большая таблица, загружается пакетами, изменяется редко:
   * запросы читают малую часть колонок, таблица широкая — **`ao_column` + `zstd`**;
   * запросы читают почти все колонки или колонок мало — **`ao_row` + `zstd`**.
3. Секционированная таблица — решайте для каждой группы секций отдельно (раздел 4).
4. Staging-таблицы, которые живут минуты, — heap или `ao_row` без сжатия, `DISTRIBUTED RANDOMLY`.
