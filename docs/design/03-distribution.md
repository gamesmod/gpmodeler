# 3. Распределение данных

Каждая таблица в Greenplum и Cloudberry имеет политику распределения: правило, по которому строка
попадает на тот или иной сегмент.

## Политики

```sql
-- по хешу от значений колонок
CREATE TABLE sales (...) DISTRIBUTED BY (customer_id);

-- равномерно, без привязки к значению
CREATE TABLE events_raw (...) DISTRIBUTED RANDOMLY;

-- полная копия на каждом сегменте (GP6+, CBDB)
CREATE TABLE currencies (...) DISTRIBUTED REPLICATED;
```

Если политика не указана, сервер выбирает её сам: обычно это первичный ключ или первая колонка
подходящего типа, а при `gp_create_table_random_default_distribution = on` — `RANDOMLY`. Сервер
при этом выводит предупреждение. **Не полагайтесь на значение по умолчанию**: первая колонка часто
оказывается датой или кодом с малым числом значений, и таблица получается перекошенной.

## Как выбрать ключ `DISTRIBUTED BY`

Хороший ключ одновременно:

1. **Имеет высокую кардинальность** — значений намного больше, чем сегментов. Идентификаторы
   клиентов, счетов, устройств подходят; пол, статус, регион — нет.
2. **Распределён равномерно** — нет значений, на которые приходится заметная доля строк.
   Опасны `NULL`, «неизвестный клиент» с ключом `-1`, служебные значения: все такие строки
   окажутся на одном сегменте.
3. **Используется в соединениях** с другими большими таблицами. Если две большие таблицы
   распределены по ключу соединения с одинаковым типом, соединение выполняется локально на каждом
   сегменте (colocated join), без `Redistribute Motion`.
4. **Не меняется.** Обновление колонки ключа распределения физически переносит строку на другой
   сегмент. В GP6 и новее это разрешено, но дорого.

Чего избегать в ключе:

* **Даты и время.** Загрузка за один день попадает на один сегмент, а запросы с фильтром по дате
  работают на одном сегменте вместо всех. Дата — кандидат для секционирования, а не распределения.
* **Колонки, по которым часто фильтруют одним значением.** `WHERE region_id = 5` при распределении
  по `region_id` нагружает один сегмент.
* **Лишние колонки в составном ключе.** Составной ключ помогает только если соединения идут по
  всем его колонкам. Таблица, распределённая по `(customer_id, account_id)`, не будет локально
  соединяться с таблицей, распределённой по `customer_id`.
* **Типы с плавающей точкой и длинные строки.** Работать будет, но целочисленные ключи хешируются
  быстрее и надёжнее совпадают между таблицами.

### Совместное размещение (colocation)

Выберите для модели несколько «осей» распределения — обычно это центральные сущности предметной
области (клиент, договор, счёт) — и распределяйте по ним все большие таблицы, которые с ними
соединяются. Пример для банка:

| Таблица | Строк | Распределение | Почему |
|---|---|---|---|
| `accounts` | 50 млн | `account_id` | центральная сущность |
| `transactions` | 20 млрд | `account_id` | соединение с `accounts` и `balances` локально |
| `balances_daily` | 15 млрд | `account_id` | то же |
| `customers` | 10 млн | `customer_id` | соединяется с `accounts` по `customer_id`, `Redistribute` по 50 млн строк приемлем |
| `branches` | 3 тыс | `REPLICATED` | маленький справочник |

Одинаковым должен быть не только набор колонок, но и **тип** колонок: `int` в одной таблице и
`bigint` в другой, `varchar` и `numeric` для одного и того же кода — частая причина лишних
перемещений. Совместимость определяется ещё и классом операторов хеширования: таблица, созданная
с устаревшими классами (`gp_use_legacy_hashops = on`, так бывает после миграции со старых версий),
не соединяется локально с таблицей на современных классах. После миграций проверяйте планы
ключевых запросов.

## Когда `RANDOMLY`

* Промежуточные (staging) таблицы, которые загружаются целиком и сразу перекладываются дальше.
* Таблицы без хорошего кандидата в ключ, которые читаются только полным сканированием с агрегацией.
* Временное решение, пока ключ не выбран: перекоса не будет, но и локальных соединений тоже.

Уникальные ограничения и первичный ключ на таблице `RANDOMLY` создать нельзя.

## Когда `REPLICATED`

Маленькие и редко меняющиеся справочники (валюты, календарь, филиалы, коды операций), которые
соединяются с большими таблицами. Каждое соединение с реплицированной таблицей локально.

Ограничения: таблица занимает место на каждом сегменте, а каждая запись выполняется на всех
сегментах. Ориентир — до сотен тысяч строк и десятков мегабайт; для больших объёмов лучше
распределение по ключу и `Broadcast Motion` при необходимости.

## Перекос данных (skew)

Перекос — неравномерность числа строк по сегментам. Запрос на перекошенной таблице работает
со скоростью самого загруженного сегмента, а при нехватке места на нём упирается в его диск.

Быстрая проверка:

```sql
SELECT gp_segment_id, count(*)
FROM sales
GROUP BY 1
ORDER BY 2 DESC;
```

Отношение максимума к среднему больше 1,1–1,2 — повод разбираться. Для обзора по всей базе есть
представления `gp_toolkit.gp_skew_coefficients` и `gp_toolkit.gp_skew_idle_fractions` (на больших
базах они работают долго, запускайте их вне пиковых часов).

Бывает и **перекос обработки** (processing skew): данные распределены равномерно, но
промежуточный результат конкретного запроса (после фильтра или соединения) собирается на одном
сегменте. Он виден в `EXPLAIN ANALYZE` по разнице строк между сегментами.

## Изменение распределения

```sql
ALTER TABLE sales SET DISTRIBUTED BY (account_id);
ALTER TABLE sales SET DISTRIBUTED RANDOMLY;
ALTER TABLE sales SET WITH (REORGANIZE = true);  -- перераспределить заново по текущей политике
```

Команда перезаписывает таблицу целиком и держит эксклюзивную блокировку, поэтому на больших
таблицах её планируют как миграцию. Дешевле выбрать ключ правильно на этапе модели.
