# 8. Эксплуатация, антипаттерны и чек-лист

Модель живёт вместе с данными. Часть решений проявляется только после месяцев загрузок, поэтому
обслуживание стоит закладывать при проектировании.

## Статистика

* Выполняйте `ANALYZE` после каждой значимой загрузки, особенно после `EXCHANGE PARTITION` и
  создания новых таблиц. Без статистики GPORCA строит плохие планы: неверно выбирает сторону для
  `Broadcast`, недооценивает число строк.
* Для секционированных таблиц собирайте статистику по изменившимся секциям; статистику корневой
  таблицы GPORCA строит из статистики секций (в GP6 — с участием параметра
  `optimizer_analyze_root_partition`).
* `analyzedb` анализирует только изменившиеся таблицы и секции, удобен для регулярного запуска.
* Колонки, по которым никогда не фильтруют и не соединяют, можно исключить из сбора статистики,
  чтобы ускорить `ANALYZE` широких таблиц.

## VACUUM и раздувание (bloat)

* **Heap-таблицы:** регулярный `VACUUM` после массовых `UPDATE`/`DELETE`. Автоочистка в Greenplum
  для пользовательских таблиц по умолчанию не работает так, как в PostgreSQL, поэтому
  обслуживание планируйте явно. `VACUUM FULL` переписывает таблицу целиком и блокирует её —
  используйте только при сильном раздувании.
* **AO-таблицы:** `VACUUM` переписывает сегментные файлы, в которых доля удалённых строк превышает
  `gp_appendonly_compaction_threshold` (по умолчанию 10 %). Если AO-таблицу приходится часто
  чистить, вероятно, для неё неверно выбрано хранение.
* Каталог тоже раздувается от массового создания и удаления временных объектов. Регулярно
  выполняйте `VACUUM` по системным таблицам.
* Представления `gp_toolkit.gp_bloat_diag` и `gp_toolkit.gp_bloat_expected_pages` показывают
  раздутые таблицы.

## Мониторинг модели

Регулярно проверяйте:

* перекос данных по сегментам (раздел 3);
* таблицы без статистики (`gp_toolkit.gp_stats_missing`);
* число секций и файлов на крупнейших таблицах;
* рост секции по умолчанию;
* планы ключевых отчётов: не появились ли новые `Redistribute Motion` по большим таблицам.

## Антипаттерны

| Антипаттерн | Чем плохо | Что делать |
|---|---|---|
| Распределение по дате, статусу, региону | перекос, работа на одном сегменте | распределение по идентификатору сущности, дата — в секционирование |
| Распределение по умолчанию | ключом становится случайная первая колонка | всегда указывать политику явно |
| Тысячи мелких секций | раздувание каталога, медленное планирование, миллионы файлов | крупнее гранулярность, архив — во внешние таблицы |
| Колоночное хранение для маленьких таблиц | много мелких файлов, нет выигрыша | heap или `ao_row` |
| OLTP-нагрузка: построчные вставки и обновления | распределённые транзакции на каждую строку | пакетная загрузка, OLTP в отдельной СУБД |
| Разные типы у колонок соединения | лишние `Redistribute Motion` | единые типы для ключей во всей модели |
| EAV («сущность–атрибут–значение») | огромные таблицы, самосоединения, нет типизации | явные колонки; редкие атрибуты — в отдельную таблицу |
| `UPDATE` больших AO-таблиц | раздувание, блокировки | пересборка через новую таблицу или обмен секций |
| Много индексов «на всякий случай» | медленная загрузка, место на всех сегментах | индексы только под выборочные запросы |
| Отсутствие `ANALYZE` после загрузки | плохие планы | `ANALYZE` или `analyzedb` в каждом процессе загрузки |
| Сотни одновременных мелких запросов | очередь на координаторе и ресурсах | группы ресурсов, пулер соединений, кеширующие витрины |

## Чек-лист ревью физической модели

Для каждой большой таблицы:

- [ ] Политика распределения указана явно.
- [ ] Ключ распределения имеет высокую кардинальность, не содержит дат и массовых `NULL`.
- [ ] Ключ совпадает с ключом соединения с другими большими таблицами, типы колонок одинаковые.
- [ ] Перекос проверен на реальных или реалистичных данных.
- [ ] Секционирование есть только там, где запросы фильтруют по ключу секций; ключ секций ≠ ключ
      распределения; число секций — сотни, не тысячи.
- [ ] Хранение выбрано по профилю нагрузки: heap для изменяемых, AO для пакетно загружаемых,
      колоночное для широких.
- [ ] Сжатие задано и подобрано на выборке данных.
- [ ] Первичный ключ и уникальные ограничения включают ключ распределения.
- [ ] Ссылочная целостность, которую СУБД не проверяет, контролируется в загрузке.
- [ ] Индексы обоснованы конкретными запросами.

Для модели в целом:

- [ ] Выбраны оси распределения (центральные сущности) и им следуют все связанные большие таблицы.
- [ ] Мелкие справочники — `DISTRIBUTED REPLICATED`.
- [ ] Есть календарь и служебные строки «неизвестно» в измерениях.
- [ ] Именование единообразное, на таблицах и неочевидных колонках есть комментарии.
- [ ] Процессы загрузки делают `ANALYZE`, обслуживание (`VACUUM`, контроль перекоса) запланировано.
