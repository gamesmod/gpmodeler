# 2. Архитектура MPP и почему она меняет правила

Greenplum и Apache Cloudberry — массивно-параллельные (MPP) СУБД на основе PostgreSQL с
архитектурой shared-nothing. Чтобы понимать рекомендации следующих разделов, достаточно знать
несколько вещей.

## Координатор и сегменты

* **Координатор** (в GP6 — master) принимает подключения, хранит глобальный каталог, строит план
  запроса и собирает итоговый результат. Пользовательских данных на нём нет.
* **Сегменты** — отдельные экземпляры PostgreSQL, каждый хранит свою часть строк каждой таблицы.
  На одном сервере обычно работает несколько основных сегментов, у каждого есть зеркало на другом
  сервере.
* **Interconnect** — сеть между сегментами, по которой они обмениваются строками во время
  выполнения запроса.

Запрос выполняется параллельно на всех сегментах. Время ответа определяется **самым медленным
сегментом**, поэтому равномерность распределения данных и нагрузки важнее, чем в обычном PostgreSQL.

## Motion-операторы

Когда строкам, которые нужно соединить или сгруппировать, не хватает «встречи» на одном сегменте,
план добавляет операторы перемещения:

| Оператор | Что делает | Когда появляется |
|---|---|---|
| `Redistribute Motion` | перехеширует строки по новому ключу и рассылает их по сегментам | соединение или группировка не по ключу распределения |
| `Broadcast Motion` | копирует все строки таблицы на каждый сегмент | одна из сторон соединения маленькая |
| `Gather Motion` | собирает результат на координаторе | почти в каждом запросе, на последнем шаге |

Каждый `Redistribute` или `Broadcast` — это сеть, память и иногда спилл на диск. Хорошая
физическая модель делает так, чтобы самые тяжёлые и частые соединения выполнялись вообще без
перемещений. Как этого добиться, описано в разделе 3.

Проверить план можно командой `EXPLAIN` (или `EXPLAIN ANALYZE` на тестовых данных): ищите в нём
слова `Motion` и смотрите, сколько строк через них проходит.

## Оптимизаторы

В Greenplum и Cloudberry два планировщика:

* **GPORCA** — оптимизатор на основе стоимости, разработанный для MPP. Включён по умолчанию
  (`optimizer = on`), лучше работает со сложными аналитическими запросами, секционированными
  таблицами и коррелированными подзапросами.
* **Postgres planner** — классический планировщик PostgreSQL с доработками для MPP. Используется,
  когда GPORCA не поддерживает конструкцию запроса или выключен.

Оба опираются на статистику, поэтому `ANALYZE` после загрузки обязателен (раздел 8).

## Что из этого следует для модели

1. **Ключ распределения — главное физическое решение.** Он определяет и равномерность данных,
   и то, какие соединения будут локальными.
2. **Рабочая нагрузка — аналитическая.** Массовые загрузки и сканирования больших объёмов
   выполняются эффективно; множество мелких транзакций с точечными `UPDATE`/`INSERT` — нет.
   OLTP-нагрузку держите в отдельной СУБД и загружайте в хранилище пакетами.
3. **Число файлов имеет значение.** Каждая таблица, секция и (для колоночных таблиц) колонка
   хранится в отдельных файлах на каждом сегменте. Тысячи мелких секций превращаются в сотни
   тысяч файлов (раздел 4).
4. **Ограничения целостности работают иначе.** Уникальность проверяется только локально на
   сегменте, поэтому она требует включения ключа распределения; внешние ключи не проверяются
   (раздел 6).
