# 4. Секционирование

Секционирование делит таблицу на части по значению колонки — обычно по дате. В MPP оно работает
**поверх** распределения: каждая секция распределена по сегментам по той же политике, что и вся
таблица. Распределение отвечает за параллелизм, секционирование — за то, чтобы читать меньше.

## Зачем секционировать

* **Отсечение секций (partition pruning).** Запрос с фильтром `WHERE sale_date >= '2026-10-01'`
  читает только нужные секции.
* **Управление жизненным циклом.** Удаление старых данных — `DROP` или `TRUNCATE` секции вместо
  `DELETE` миллиардов строк. Архивные секции можно перевести на другое хранение или сжатие.
* **Загрузка через обмен секций.** Новая порция готовится в отдельной таблице и подменяет секцию
  командой `EXCHANGE PARTITION` — почти мгновенно и без долгих блокировок основной таблицы.

## Когда не нужно

* Таблица небольшая (ориентир — меньше сотни миллионов строк или единиц гигабайт на сегмент).
* Запросы не фильтруют по кандидату в ключ секционирования.
* Нет задачи удалять или архивировать данные порциями.

Секционирование увеличивает число объектов в каталоге и файлов на диске, замедляет планирование
и `ANALYZE`. Без пользы от отсечения оно только вредит.

## Выбор ключа и гранулярности

* Ключ — колонка, по которой фильтруют большинство запросов: дата операции, дата отчёта, период.
* **Ключ секционирования и ключ распределения должны быть разными колонками.** Секционирование
  по дате при распределении по дате даёт перекос и в данных, и в обработке.
* Гранулярность подбирайте так, чтобы секция была достаточно крупной: месяцы или недели чаще, чем
  дни. Дневные секции на 10 лет — 3650 секций; у колоночной таблицы на 100 колонок и 96 сегментов
  это десятки миллионов файлов.
* Многоуровневое секционирование (дата и, например, регион) применяйте только если оба уровня
  реально участвуют в фильтрах. Число секций перемножается.
* Ориентир: суммарно сотни секций на таблицу, а не тысячи.

## Синтаксис

### Классический синтаксис Greenplum (GP6, GP7, CBDB)

```sql
CREATE TABLE sales (
    sale_id     bigint,
    account_id  bigint,
    sale_date   date,
    amount      numeric(18, 2)
)
WITH (appendoptimized = true, orientation = column, compresstype = zstd, compresslevel = 5)
DISTRIBUTED BY (account_id)
PARTITION BY RANGE (sale_date)
(
    START (date '2025-01-01') INCLUSIVE
    END   (date '2027-01-01') EXCLUSIVE
    EVERY (interval '1 month'),
    DEFAULT PARTITION other
);
```

`START/END/EVERY` генерирует секции автоматически, `PARTITION BY LIST` задаёт секции по списку
значений, `SUBPARTITION BY` и `SUBPARTITION TEMPLATE` — второй уровень.

### Декларативный синтаксис PostgreSQL (GP7, CBDB)

```sql
CREATE TABLE sales (...)
USING ao_column
DISTRIBUTED BY (account_id)
PARTITION BY RANGE (sale_date);

CREATE TABLE sales_2026_10 PARTITION OF sales
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

В GP7 и Cloudberry секции — обычные таблицы, их можно присоединять и отсоединять
(`ATTACH PARTITION` / `DETACH PARTITION`). Классический синтаксис поддерживается для совместимости
и раскрывается в те же объекты.

## Секция по умолчанию

`DEFAULT PARTITION` ловит строки, не попавшие ни в одну секцию, и защищает загрузку от ошибок.
Обратная сторона: запросы по диапазону часто вынуждены читать и её, а добавление новой секции
требует проверки (и в GP6 — разделения, `SPLIT`) секции по умолчанию. Практика:

* держите секцию по умолчанию пустой и контролируйте её мониторингом;
* создавайте секции заранее, на несколько периодов вперёд;
* если источник гарантирует корректные даты, обходитесь без секции по умолчанию.

## Разное хранение для разных секций

Секции одной таблицы могут иметь разное хранение. Типовая схема:

| Возраст данных | Хранение | Зачем |
|---|---|---|
| текущий месяц | heap или `ao_row` со слабым сжатием | частые догрузки и исправления |
| последний год | `ao_column`, `zstd` уровень 3–5 | основная аналитика |
| архив | `ao_column`, `zstd` высокий уровень, или внешняя таблица | редкий доступ, экономия места |

## Обмен секций при загрузке

```sql
CREATE TABLE sales_load (LIKE sales) WITH (...) DISTRIBUTED BY (account_id);
-- загрузить и проверить данные в sales_load, выполнить ANALYZE
ALTER TABLE sales EXCHANGE PARTITION FOR (date '2026-10-01') WITH TABLE sales_load;
```

Таблица для обмена должна совпадать с секцией по колонкам, политике распределения и хранению.
